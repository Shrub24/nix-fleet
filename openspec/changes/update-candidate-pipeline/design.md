# Design

## Context

See proposal.md - Why. Current state:

- `flake.nix` is generated by flake-file (`nix run .#write-flake`); auto-follow is disabled because it makes generation depend on the previous generated file and can move locks (`docs/contracts/flake-inputs.md`).
- Routine `ci.yml` is evaluation-only by decision; real builds run only in `build-push-cache.yml`, which has `workflow_dispatch` and `workflow_call` and builds `.#checks` by default. It has no input naming the revision to build.
- `update-packages` stages each package in a disposable jj workspace and reports on stdout, JSON and markdown. A scheduled workflow runs it weekly and opens a PR, unbuilt.
- Renovate has never opened a PR here: the app was not enabled on the repository. Its config is weekly lock maintenance with automerge off.
- The repository has no rulesets, no branch protection, and `allow_auto_merge` is off.
- niks3 OIDC trust is `main` only (policy in nix-homelab; not re-verified here).
- Verified on this repository (scratch ruleset, since removed): a ruleset requiring a status check, with no bypass actors and no pull-request rule, rejects a direct push of a commit that lacks the status ("Required status check ... is expected") and accepts a fast-forward push of the same commit once the status is posted on its SHA. Refs outside `refs/heads` (for example `refs/candidates/*`) can be pushed. GitHub documentation states a PR whose head becomes reachable from the base is marked merged, even if branch protection was not satisfied.
- Not verified, to settle during implementation: ruleset `integration_id` pinning of the required status to one App; whether a skipped job satisfies a required status; the OIDC claims for a `pull_request`-triggered reusable workflow and for an Environment.

## Goals / Non-Goals

**Goals**

- One lifecycle for every update PR: prepare, build exact SHA, evidence, promote by policy.
- Evidence enforced by GitHub, not by trust in our promoter.
- The tree that is built and cached is the tree that lands on `main`.
- Reusable by consumers with only a policy difference.

**Non-Goals**

- Cross-repository orchestration; the flake input graph orders fleet before consumers.
- A staging branch, a second PR lifecycle, or a merge queue. Merge queue is not available on personal-account repositories as far as I know; verify before relying on that.
- Self-hosted Renovate or `postUpgradeTasks`.
- Building consumers' host closures from the fleet repository.
- Consumer package-updater migration and consumer promotion rollout (follow-on changes).
- Automatic bisection of a broken input (the exclusion list is the day-one control).

## Decisions

### 1. Promote by fast-forward push, not by merging a PR

The candidate may be a child of the source head, so merging the source PR cannot land it, and pushing to the source branch would make Renovate treat its branch as modified. A direct fast-forward of the candidate SHA to `main` lands exactly the tested commit and marks the source PR merged by reachability.

- Alternative: push the child onto the source branch. Rejected: foreign commit on a bot branch, Renovate overwrites it on rebase, and it needs `gitIgnoredAuthors`, which is unverified.
- Alternative: an integration PR containing the candidate. Kept as the fallback if direct promotion proves unreliable. It restores PR-based checks at the cost of a second PR lifecycle.
- Alternative: merge queue. Not available to personal repositories (unverified), and a generated child cannot be injected into a queue's merge group.

### 2. No ruleset bypass for the promoter

The App obeys the same required status as everyone else. A promoter bug then cannot land an unvalidated commit, because GitHub rejects it. Fast-forward-only push semantics make the base-moved case fail by itself, so no separate compare-and-swap code is needed. The ruleset omits the pull-request rule; the required status is the gate, and human PRs still merge through the normal button once their status exists.

- Alternative: App as bypass actor. Documented as available for personal repositories at the API level, but it removes the enforcement above and is only a fallback.

### 3. Evidence is a commit status on the candidate SHA, posted explicitly

Required statuses attach to a SHA. A `pull_request` job reports on the PR head, which differs from the candidate when preparation adds a child. Posting explicitly on the candidate SHA gives one code path for both cases. The required context name is stable and the job that posts it exists on every PR, so documentation-only PRs report it (a skipped or missing status would block every human PR).

- Prefer a dedicated App as the status source and pin the required status to it. A status from `GITHUB_TOKEN` is attributable only to the shared Actions identity; acceptable for a single-owner repository, weaker if collaborators appear.

### 4. Build by SHA, not by merge ref

`pull_request` workflows check out `refs/pull/N/merge`. The pipeline fetches and builds the explicit candidate SHA so the evidence belongs to the commit that will be promoted. `build-push-cache.yml` gains an input naming the revision to build; its default behaviour (current ref) is unchanged.

### 5. Preparation is generated-file reconciliation only

`write-flake` then `nix flake lock` (no update). The pipeline never rediscovers versions, so a second run on its own output is a no-op, which is the invariant that makes reruns safe. This is a risk in this repository because `write-flake` can move locks when auto-follow is enabled; it is disabled by policy, and a fixed-point check is part of the work so a regression is detected.

Preparation also owns nothing else: it stages exactly `flake.nix` and
`flake.lock`, and refuses any other path that moved during regeneration. The write
set is the same rule the package updaters follow, and it matters for the same
reason — a preparation commit that absorbed an unrelated change would carry it
into a candidate nobody reviewed as such. An unexpected path fails the run by
name instead.

### 6. The native producer replaces Renovate lock maintenance

`nix flake update` followed by the package updaters, in that order, so compiled outputs and their hashes are computed against the lock that will land. Owning the refresh gives an exclusion list (Renovate's `lockFileMaintenance` cannot skip an input), cumulative reporting, and later cache-aware policy. Renovate keeps what needs registry or release intelligence: tagged flake inputs, Actions, OCI.

- Alternative: Renovate lock PR plus a stacked package commit. Rejected: needs `gitIgnoredAuthors` or a branch we must not touch.
- Alternative: absorb tag discovery into the producer. Deferred; revisit if release-age gating and changelogs are not worth keeping in Renovate.

### 7. Renovate configuration

Keep the `github-actions` manager and a custom regex manager for annotated tagged-input declarations in the flake-file modules, and remove the built-in `nix` manager from `enabledManagers`. The regex manager is text extraction plus a semver lookup against the GitHub tags or releases datasource and needs no Nix machinery. `lockFileMaintenance` is dropped because the producer replaces it, and Renovate has no lock step for a regex-managed file, so the lock is reconciled by candidate preparation. Also disable automerge.

### 8. Privilege boundary

Evaluation of updated inputs, updaters and builds run in jobs without the App credential. The promoter runs from the default branch's workflow definition and receives the candidate SHA. Builder and cache-write access for candidate builds is scoped by a GitHub Environment claim in the OIDC trust, not by branch-name prefix. That trust lives in nix-homelab and is a prerequisite.

### 9. Candidate-time cache publication is intentional

Superseded or rejected candidates may still contain useful compiled dependencies, and the cache is garbage-collected. Publication is gated by identity scope, not by merge approval.

### 10. Cache verification

After the build, a fetch-only check evaluates the candidate against the substituters with builders disabled and requires no derivation to be built. It is the only mechanism that distinguishes "built" from "available to consumers".

### 11. Closure scope

nix-fleet builds its own checks, fixtures and packages. Checks do not cover every package, so an aggregate check includes them. A fleet build cannot warm consumers' host closures; consumers expose their host toplevels as checks, which keeps `checks.<system>` the canonical workload.

### 12. Consumer acceptance binds to a revision

Applying the acceptance label posts an `update-accepted` marker on the commit the
label event concerns — `accept.yml`, defined on the default branch, takes the head
from its own `pull_request_target` payload — and the promoter requires the marker
on the source revision it is about to promote. A push after the label leaves the
newer revision unmarked, so acceptance lapses without anyone removing the label,
and promotion refuses by name.

- Alternative: compare the label's timestamp with the source commit's date, and
  refuse when the label is older. Implemented first, then withdrawn: a commit's
  dates describe when it claims to have been written, not when it reached the pull
  request. A contributor or a bot can push a commit created before the label, and
  that revision would be promoted on someone else's acceptance.
- Alternative: remove the label whenever the head changes, so presence implies the
  current revision. Rejected: every trigger reliable enough to do it is either the
  pull request's own workflow file (the file the whole boundary distrusts) or a
  timestamp, so it needs a backstop anyway.
- Alternative: a required check name for the marker. Rejected: a required name
  must pass for every change, including ones nobody is accepting. The marker is a
  commit status that only the promoter reads.

### 13. Deferred inputs are declared beside package registration

The exclusion list is a flake-module option next to `packageUpdates.packages`, each entry an input name with a non-empty reason, mirroring the write-set rule that shared paths need a rationale. A manual run can also pass an explicit subset. One place serves the fleet and consumers, and a deferral is visible in review.

### 14. The producer's updaters and its publication are separate jobs

`nix-update` executes each package's update script, so the job that runs the batch
is a code-execution job. It therefore holds no credential: it records the proposal
as a git patch plus the report files. A second job selects the `automation`
environment, applies that patch to a clean checkout of the revision the refresh
ran on, and opens the pull request. The proposal crosses as data, and the patch is
refused outright when its base has moved, because a wholesale `flake.lock` rewrite
taken from an older revision would revert whatever landed in between.

The alternative — one job ordering "run updaters, then mint the token" — protects
nothing, since a single job's steps share an environment and the token is minted
into it. Consumers pay no share of this: the job names and the environment are the
repository's own, and the reusable workflow keeps them inside itself.

### 15. The batch's exit status carries whether its result is proposable

`update-packages` exits 0 for a clean run, 1 for a run that completed with per-item
failures, and 2 when nothing can be proposed because the tooling, registry or
adoption failed. The same value is the report's `outcome` (`complete`, `partial`,
`aborted`), so a caller reads it from either without re-deriving it, and the
publisher keys off it. A failed updater's own non-zero code stays in the report and
on stdout rather than becoming the batch's, and an adoption that fails part-way
ends the batch: promoting half a transaction is worse than proposing nothing.

The alternative, "non-zero means do not propose", is what made a single failing
package silently suppress the whole refresh: the workflow never reached its PR step
and the only trace was a log line.

The publisher requires the status and the report to agree — `complete` with 0 or
`partial` with 1 — and both artifacts to exist and be non-empty. Without that, a
run whose markdown write failed would leave a report saying `complete` beside a
non-zero status: the report is the evidence, and evidence about a run that did not
finish must not propose a tree. The producer check executes the decision for the
consistent pairs, the contradictory pairs and the missing-artifact cases.

## Risks / Trade-offs

- [A required status that is missing on some PRs blocks them] → the posting job exists on every PR and reports even when nothing needs building.
- [Promotion lands a commit built on an old base] → fast-forward-only push fails and the candidate is rebuilt.
- [Open update PRs go stale after `main` moves] → a push-to-`main` trigger re-prepares them.
- [One broken input blocks every candidate] → exclusion list and manual input subset on day one; bisection later.
- [Candidate build executes upstream code on builders] → bot-authored same-repository PRs only, no App token in the job, Environment-scoped trust.
- [Status posted by the shared Actions identity] → move to a dedicated App for the required status.
- [GitHub behaviour assumed above is wrong] → unverified items are implementation tasks with an explicit fallback (integration PR).
- [Flaky runners fail an automerge gate] → the failure is reported once, with the stage that failed named; no retry (see below).
- [Daily builds are expensive] → relies on cache substitution of unchanged derivations; observe cost before enabling a daily schedule.

## Migration Plan

1. Install and enable the Renovate and promotion Apps; confirm Renovate opens a PR here.
2. Land the pipeline with promotion disabled; run it on the native PR and observe.
3. Add the ruleset and enable `auto` promotion for the native PR only.
4. Retarget `package-updates-refresh.yml` to the producer and remove the lock maintenance from `renovate.json`.
5. Add the tagged-input regex manager once the first tagged input exists.
6. Document the reusable workflow for consumers; consumer adoption follows separately.

Rollback: disable the ruleset's required status and set the promotion policy to `label`, leaving candidate builds and cache publication in place.

## Implementation decisions

Settled while applying the change; the rationale is in `context/update-candidates.md`.

- **Promotion reads `status` events, not a pull-request branch.** The promoter runs
  from the default branch, and its candidate status must come from the App, since a
  `GITHUB_TOKEN` status does not trigger it. Decision 1 is unchanged.
- **Human pull requests get the same status, context `update-candidate`.** The
  ruleset's required status also gates a merge by hand. It is posted by the same
  job as an automation candidate's (`candidate.yml` in `mode: human`), from the
  default-branch entry point, rather than from `ci.yml`. The context is not
  `candidate` because a required name that a workflow or job also produces would
  require both the check and the status to pass. The promoter ignores statuses on
  commits without a candidate ref, so it cannot promote a human change.
- **The privilege boundary is which file defines a step, not the order of steps
  inside it.** A `pull_request` event runs the pull request's version of the
  workflow file, and a local (`./`) reusable workflow is taken from the caller's
  commit, so a repository secret referenced by name is reachable from the revision
  it is meant to distrust. The entry point therefore moved to `pipeline.yml`,
  triggered by `workflow_run`, which runs the default branch's definition and
  resolves the revision from the API; the App key moved to an `automation`
  environment restricted to `main`, whose secrets a pull-request job cannot
  select; and the candidate ref is now published with the workflow token, which
  cannot post the status that authorises promotion.
- **No `pull_request: labeled` trigger on the promoter.** That is the same shape
  the boundary forbids — a pull-request-defined file holding the push credential.
  Acceptance re-validates instead: `labeled` is in `ci.yml`'s trigger list, so
  applying the label re-runs the pipeline (preparation is a no-op, the build is a
  cache hit), which reposts the status the promoter consumes. The reuse is real
  validation rather than a renewal, and it costs no rebuild. `accept.yml` also
  reads that same label event, and it holds only `statuses: write`.
- **Validation diagnostics are three jobs, not `if: always()` steps.** The
  commands stay in one definition called from two places; they are split into
  `format`, `evaluate` and `consistency` so a formatting failure no longer hides
  whether evaluation also fails, and each failure names itself. Three jobs cost two
  extra runner starts and Nix installs, which is cheaper than the contributor
  round-trip the sequential version caused, and for a workflow-only revision the
  formatting job is the only meaningful check. `if: always()` steps were the
  alternative; the reviewer's point is that they keep the reader interpreting a
  job graph to learn what ran.
- **A consumer calls the pipeline; it does not copy it.** `pipeline.yml` gained
  `workflow_call`, joining the other trigger-only files. It was written as a copy
  on the argument that its content is policy, but that policy is already data —
  the producer allowlist, the build selection and the promotion policy are all
  repository variables — and what is left is routing that has been corrected
  repeatedly under review. A called workflow's local `./` paths resolve from the
  caller's commit, which is the pinned ref, so a consumer needs no copy of
  `candidate.yml` or `validate.yml` either. What a consumer owns is a thin trigger
  per event, its variables, its environment, the permission union and
  `secrets: inherit`.
- **Cache verification is post-merge and never gates a candidate.** This replaced
  an earlier decision to verify inside the candidate pipeline. Gating on
  availability coupled every dependency update to the cache server's health while
  saying nothing about whether the revision is correct, and the only consumer of a
  same-run verdict was the promotion gate. `verify-cache.yml` now runs on a push to
  `main` and on dispatch, reads the **public** substituter route — substitution is
  public although the write API is not — and needs no tailnet identity, no OIDC and
  no secret. It asks `nix path-info` about each realised closure root: uploads are
  atomic per closure, so a served root means its closure was committed, and
  `--recursive` would be thousands of requests proving nothing more. Rejected
  alternatives: reading the upload daemon's SQLite queue (internals, and a dead
  daemon looks like an empty queue); scraping the drain timeout's warning (emitted
  by a post step, so nothing inside the job can react, and it binds to upstream
  wording); a repair push (shares the daemon's server and token, so it rescues only
  the queue-did-not-send case — which is the case being reported — while risking
  doubled upload time); and restricting the substitution to `--max-jobs 0
--builders ''` on a plain store (that passes for any path already present, so it
  tests the runner's emptiness rather than the cache).
- **A promoted revision is pinned, one aggregate root per system, by a workflow of
  its own.** Pinning turns a point-in-time observation into a guarantee, because the
  cache's GC excludes pinned closures. Rolling names (`CACHE_PIN_NAME-<system>`)
  mean supersession is a repoint — no delete, which would need admin. The pin lives
  in `pin-cache.yml`, dispatched by `promote-candidate.yml`, because a pin name
  means "the fleet's current main": promotion is the event that lands a revision the
  pipeline built, whereas `verify-cache.yml` on a push is a measurement whose colour
  nothing may depend on. `pins create` fails by name when a path is absent, so the
  pin asserts presence itself and a revision whose publication was incomplete never
  moves a name that stays on the previous good closure. A pin names one path, so
  `checks.<system>.cache-root` aggregates the build selection: its closure covers
  every published output, including `checks.packages`.
- **Outputs never imply success.** `build-push-cache.yml` sets `build` only on
  success, `verify-cache.yml` has no success output, and the status job treats a
  skipped job, a missing result or an absent output as failure. The stage that
  failed is named in the status description.
- **No retry.** Retry was dropped: the only failure it ever covered was a
  hosted-runner shutdown in the native build step, and that path no longer runs —
  routine CI is evaluation-only and real builds go through the fleet builders.
  Repeating an uncached package build on a deterministic failure spends more than
  it saves, and the stage is named in the status, so the first failure's log is
  the diagnostic.
- **A stale source is merged, not refused.** Refusing a source that is behind
  `main` and leaving the refresh to the branch owner reads as simpler and keeps
  `main` linear, and the review that raised it argued for it. It was declined: a
  producer re-run whose diff is unchanged writes no commit, so its branch stays
  behind `main` and the proposal can be neither promoted nor refreshed without
  rewriting a branch a bot owns. Merging in preparation makes the pipeline its own
  refresher, and the merge commit is prepared before validation, so the commit
  that was validated is the one promoted.
- **Merge `main` into the source; do not rebase.** Decision 3 did not cover a
  moved `main`. A merge keeps the source head reachable, so the pull request is
  marked merged.
- **Cache verification runs in its own job** (decision 10). The check is a dry run
  in an empty chroot store with builders disabled, so anything the cache does not
  serve shows as "will be built". A verdict inside the build job would race the
  upload daemon's post-step drain.
- **Retry is a second job,** not a rerun. A running workflow cannot rerun itself.
- **The producer run is explicit about the lock:** `--refresh-inputs` moves every
  non-deferred input, `--input` moves named inputs, and a run that names only
  packages leaves `flake.lock` alone. The scheduled workflow passes the flag.
- **The refresh gate is dropped.** The candidate pipeline's evaluation gates the
  refreshed tree, so the workflow no longer evaluates it separately.
- **The closure build is skipped for workflow-only changes** (decision 9 is
  unchanged; this skips work the cache already holds).
- **`checks.packages` aggregates `config.packages` verbatim,** so the check adds no
  derivation of its own (decision 11).
